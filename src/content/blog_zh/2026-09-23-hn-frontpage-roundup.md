## 五角大楼称过度依赖 AI 导致对伊朗学校的导弹空袭
**870 points** · [Bloomberg](https://www.bloomberg.com/graphics/2026-iran-school-attack/)

2 月 28 日战争爆发首日，两枚战斧巡航导弹击中了伊朗南部米纳卜（Minab）的沙贾拉·塔耶巴（Shajara Tayyeba）小学，造成超过 150 人丧生，其中至少有 123 名儿童。七个月后，彭博社援引相关官员并披露了一份未公开的五角大楼内部审查报告，结论指出：过时的情报数据、平民伤亡审查机制的缺失，以及对 Palantir 旗下 Maven 智能系统的过度依赖，共同导致了这场空袭惨剧。基于无人更新的陈旧情报，该学校在系统数据库中仍被标记为伊斯兰革命卫队（IRGC）设施。Maven 从候选目标堆中将其挑出，并作为*开战首日的推荐打击目标*返回。过去需要耗费数小时的目标清单核对流程被压缩至数分钟；在最初的 24 小时内，美军共打击了 1,000 多个目标。

讨论帖中轻视的那一半，恰恰是整起事故中与软件本身无关的一半。国防部长赫格塞斯（Hegseth）此前将全军平民伤亡缓解（Civilian Harm Mitigation, CHM）团队削减了约 90%，总人数减至不足 20 人，中央司令部（CENTCOM）的分部团队更是从 10 人直接砍成了 1 人。在空袭发动前，CHM 团队中没有任何人审核过米纳卜的这一目标。官方官员直言，这既是裁员的必然结果，也是指挥层决定根本不让该团队参与初筛的体现。换句话说，Maven 支持者挂在嘴边的“人在回路中（human-in-the-loop）”，仅仅存在于组织架构图上，却彻底缺席了实操工作流。审查报告中的措辞远比一句“我们太依赖工具了”更为严厉：报告认定美国“违背了”采取一切可行措施核实目标的法定义务，“在意识到打击民用设施存在重大风险的情况下仍指示对学校建筑发动空袭，属于鲁莽行径”。这是一份关乎决策层法律责任的判定，而非系统技术精度的评估。

中央司令部给出的整改方案分为三部分：重构既定目标的更新与核验工作流、引入追踪平民活动的新型开源数据流，以及对 Maven 进行数十项升级。其中最引人注目的头条改进，是让 Maven 具备新功能以“标记人工审核可能疏漏的不一致与不准确之处，并重新审查底层情报以识别排除打击的因素”。请把这句话重读一遍：系统如今被要求去找出那些被裁撤人员原本负责发现的问题。在边际效应上，这固然是一项务实的技术补丁，但它绝不可能替代充实的人力编制。因为一个用于标记排除打击因素的模型，归根结底只是一个由人工设定阈值的概率过滤器，而那个阈值的设定本身正是灾难的根源。

讨论帖正如预期的那样截然分裂为两大阵营，且双方都有充分的立论基础，因此都值得记录。一方认为 AI 成了替罪羊：情报过时、审核仓促、最终签发命令的是活生生的人，因此应该归咎于指挥流程。另一方则指出这恰恰切中了要害：核心问题不在于 Maven 给出了错误建议，而在于 AI 让一个人手严重短缺的组织误以为自己能以处理 10 个目标的同样严谨度去处理 1,000 个目标，这种“虚假的严谨表象”具有致命的危险性。第三位评论者提到了 9 月份 CNN 的一则报道（美军基于一份由 AI 辅助分析、声称载有核武器组件的情报报告，险些在公海拦截一艘中国货轮），以此进一步论证第二阵营的观点：这形成了一种将分析判断外包并盲目继承其置信度的危险模式。

马克·里德尔（Mark Riedl）在 Bluesky 上的点评最精准地切中了真正的监管困境：*“'人为主导（human-directed）'与'人在回路（human-in-the-loop）'是极其含糊的字眼。”* 决定究竟是由人主动做出的，还是人仅仅没有行使否决权，两者有着天壤之别，但目前的任何武器采购与合规条文中都未对两者做出实质区分。

## “我们黑进了 FBI”：黑客声称掌握全体 FBI 雇员数据
**779 points** · [404 Media](https://www.404media.co/we-hacked-the-fbi-hackers-say-they-have-data-on-all-fbi-employees/)

黑客组织 ShinyHunters 声称已攻破多个与 FBI 关联的服务，并掌握了*所有* FBI 雇员及应聘者的隐私数据。404 Media 查阅了其提供的 5,000 名据称是特工人员的样本数据，其中包含姓名、家庭住址、电话号码乃至配偶信息。该组织向 404 Media 表示，他们不认为自己的计划属于敲诈勒索，而是“或许算作胁迫”，并称其动机并非为了金钱。404 Media 对潜在风险的定性非常准确，无需任何多余修饰：ShinyHunters 生态圈中的网络罪犯此前曾利用泄露的电信运营商数据，专门追踪并骚扰正在调查他们的 FBI 特工。一份包含家庭住址和家属信息的名单，与普通凭证泄漏有着本质区别。

在陷入恐慌之前，必须客观拆解已知事实。已确认的部分包括：黑客声称拥有全员数据、404 Media 查验过的 5,000 份样本，以及某些未公开具体名称的服务遭到了入侵。尚未确认的部分包括：整份名单是否真实有效、数据的新旧程度、这究竟是一次底层数据库的直接拖库还是对公开/商业数据的撞库拼凑，以及源头究竟出自 FBI 的哪套具体系统。“掌握所有 FBI 雇员的数据”目前仅是攻击者单方面的宣传口径，从历史先例来看，这类豪言的最终实际范围通常都会大打折扣。讨论中大家都不可避免地联想到了 2015 年 OPM（美国人事管理局）的 2,210 万条人事档案大泄露，但那是经过实际数据库比对验证的真凭实据。

评论区弥漫的主导情绪并非深度技术剖析，而是一种无可奈何的认命感，而这种宿命感是完全可以理解的。有评论者指出：在全美所有公民的医疗、金融和个人背景记录被源源不断聚积到各种中心化服务器的同时，从未有任何人证明过自己有能力保障超大规模数据库的绝对安全——这正是现实对话的终点。真正有价值的反思来自架构层面：这类数据集即便不被直接拖库也极具危险性。《联邦公报》（Federal Register）、选民登记册、不动产契约、法院诉讼记录以及商业数据经纪人早已将绝大多数公开碎片拼接完成；黑客数据泄露所带来的边际价值，完全取决于那些未公开的独家字段——即绑定到当前具体职务的官方身份，或者是那些反映了申请意向而非最终录用的人才库名单。

## 如何与 LLM 协同写作
**759 points** · [sockpuppet.org](https://sockpuppet.org/blog/2026/09/17/how-to-write-with-an-llm/)

这是一篇短小精悍的方法论文章，堪称近几个月来 HN 上出现过的最佳写作指南。文章开门见山给出了诊断：读者能以万亿分之一的敏锐度捕捉到模型生成的句式。这意味着无论你对它进行多么粗暴的后期润色，LLM 写出的段落依然会被一眼识破为纯粹的“生成结果”而非真正的“写作”，因此你必须亲自动笔。模型只能坐上校对席，绝不能坐上作者席。

作者的核心贡献在于提炼出了两条严苛法则。**法则一：绝不采用任何一个由 LLM 建议的词。** 这并不是因为它的建议不好，相反，正是因为它的建议太好、太流畅了，而这正是圈套所在。问题在于，前沿模型生成的每一句话都深陷于一种类似“商业杂志标题”的腔调之中；通篇由好标题堆砌而成的文章，读起来只会让人怀疑作者的真诚度。这条规则被作者定义为智力层面的“个人防护装备（intellectual PPE）”，因为你根本无法稳定定位被污染的痕迹究竟藏在何处。即便模型建议的措辞比你自己的更好，它也必须被毫不留情地废弃。**法则二：避开模型的阿谀奉承与鼓励。** 这一点更为微妙，关乎认知机制而非个人审美。如果你把初稿扔给模型，它会赞叹这是绝世金句；接着它夸你的段落结构完美，然后又吹捧你的过渡句、选词和隐喻。在每一个层次上都被如此迎合与首肯，你会彻底失去自我推敲与推翻重写的动力——而正是这种“自我重审”，构成了你个人文风与声音的灵魂所在。作者多年来惯用的一种破解技巧，是在提示词中撒谎称自己并非作者、而是一名负责筛选投稿文章的审稿编辑——这是一记极高明的招式：通过改变模型对对话对象的认知，硬生生把阿谀奉承逼成了严苛批评。

讨论帖把这套方法论进一步推广到了更广泛的工程领域，其中关于 Git Commit 提交信息的讨论尤其深刻。一位开发者报告称，他如今坚持亲手撰写所有的 Commit 提交信息和 PR 说明，仅允许模型辅助核对事实，坚决不让其润色行文。这样做的直接收益在于：为了写出提交说明，你必须强迫自己通读代码，从而真正消化并理解整个 Git Diff；而在由 Agent 大量辅助的工作流中，浮于表面的走马观花往往成了默认状态。这实际上将原文针对散文写作的逻辑无缝映射到了代码审查之中，也是即便工具拼命推销“一键生成”时，开发者依然应该坚持亲笔撰写 Commit 信息的终极理由。

另一侧的共鸣来自从读者视角的反思：读者在每一个段落中下意识地辨别模型污染的蛛丝马迹，一旦抓到破绽，整个阅读过程的愉悦感便荡然无存。还有一句更犀利的直言：如果你自己都懒得花时间去写，凭什么要求别人花时间去读？这种质问直击要害，它探讨的不再是单篇文章的质量，而是整个创作生态的博弈均衡。原文唯一有所低估的，是事实核验（Accuracy Verification）环节——多位评论者指出，这才是 LLM 真正高价值的用武之地：在不产生幻觉的前提下，严格检验论点是否能经受住底层原始文档的印证。这既不是编辑也不是写作，而是一个纯粹的校验步骤，也是模型的工具属性与作者的利益诉求达成高度一致的唯一交集。

## 25 行 Python 代码实现 Jev
**555 points** · [nobodywho.ai](https://www.nobodywho.ai/posts/jev-in-25-lines/)

连续多日霸榜的前沿“系统一（System One）”决策模型——TypeSafe 的 Jev，如今被一段短小到几分钟即可读完的脚本完整复刻。加载 GGUF 权重（演示采用 Qwen3-0.6B 量化版，512 token 上下文）、将候选选项拼装进 Prompt、对 token 进行前向推理计算、提取目标选项 token 的 logits，最后进行归一化。整整 25 行代码。原文通篇带着直白的冷嘲热讽：*“外界把 Jev 吹上了天，但我们觉得这根本没什么大惊小怪的。”* 核心论点并非指责 Jev 是骗局，而是揭露了一个事实：这套东西里真正有趣的部分，自始至终都不是模型本身。

这一视角与本周社区曝光的所有细节高度吻合。昨天讨论 OpenAI 迅速跟进 Jev 的帖子也反映了同样的规律，而本文补充了一个关键的技术实现细节：如果底层诀窍仅仅是对候选 token 的 log 概率执行单次前向传递（Single Forward Pass），那么前沿实验室无需发明任何新能力，就能轻而易举复刻其训练过程；整个商业壁垒将完全蜕化为校准算法（Calibration）和工程封装。帖子里最有价值的反驳指出了该方案容易出纰漏的地方：拿对话模型（Chat Model）充当基座模型“总是让人觉得靠不住”。因为你是从一个被专门训练用来吐出连贯散文句子的模型中强行读取概率分布，目标选项 token 的概率质量往往会被模型原本想要表达的其他句式给稀释掉。因此多位评论者强调，必须使用结构化输出（Structured Outputs）或施加约束的 Assistant 前缀，这也是为何演示脚本硬要将选项显式定义在 Prompt 内部的原因。第二项技术洞察比原文更上一层楼：由于因果掩码（Causal Masking）机制的存在，必须将选项放置在待分类的上下文内容*之前*，这样模型在构建注意力状态时才能提前获知需要关注的目标特征。

最扎实的反对意见来自一位使用 Embeddings（嵌入向量）加 Ridge Regression（岭回归）实现同等功能的开发者——训练耗时不到一秒，且由于训练集完全来自目标领域，可以天然利用保形预测（Conformal Prediction）进行置信度校准；他敏锐地指出，通用决策模型的置信度分数在架构设计上对你的具体业务数据就是未校准的。第三位评论者做出了最坦诚的中肯总结：这个 25 行的 Demo 能带你走完 80% 的路程，而剩下的 20% 全是边界情况、基础设施、API 封装和通讯协议。类比层面的辩驳往往停留在它们所设定的抽象层级，“它只是个分类器”这句话完全正确，但放之四海皆准的大实话也等于什么都没说。

## AMD Ryzen 是如何在两年内提速 50% 的？
**466 points** · [lemire.me](https://lemire.me/blog/2026/09/18/how-did-amd-ryzen-get-50-faster-in-two-years/)

Daniel Lemire 拿出了三款 8 核 X3D 桌面处理器——5800X3D（Zen 3，2022 年）、7800X3D（Zen 4）和 9800X3D（Zen 5）——对这几年的实际性能飞跃进行了量化盘点。Geekbench 6 跑分：单核成绩由 2,016 → 2,426 → 2,969；多核成绩由 11,832 → 15,508 → 18,751。这意味着在核心数量与 3D V-Cache 缓存容量完全保持一致的前提下，短短两年内单核性能提升了 47%，全核性能提升了 58%。时钟频率对此几乎没有贡献：最高加速频率仅从 4.5 GHz 提升到了 5.2 GHz（增幅仅 15%），且频率层面的收益主要由基础频率的拉高贡献。

真正的功臣是晶体管预算的爆炸式增长及其分配去向。晶体管总数由大约 110 亿颗激增至 160 亿颗（增长近 50%），且绝大部分新增的晶体管都堆在了 CPU 核心内部，而非缓存区域。具体换来的微架构升级包括：指令分派宽度（Dispatch Width）从每周期 6 条增至 8 条、每核心 L2 缓存从 512 KB 翻倍至 1 MB、L1 数据缓存从 32 KB 扩充至 48 KB、整数 ALU 从 4 个增至 6 个，而决定处理器能隐藏多少内存延迟的重排序缓冲区（Reorder Buffer, ROB）条目更是从 256 个暴增至 448 个。SIMD 向量处理单元实现了阶跃式进化而非渐进微调：Zen 3 和 Zen 4 配备的是 4 个 256 位向量单元，而 Zen 5 升级为了 4 个完整的 512 位单元，且每周期支持 2 次 512 位加载和 1 次 512 位存储。随后 Lemire 坦率指出了绝大多数媒体报道刻意忽略的前提：这些都是 Geekbench 的综合基准测试结果，具体到不同工作负载差异巨大。一条精辟的回复点出了核心实质：一位评论者分享了其经过专项调优的 Zen 5 工作负载数据——在 5.1 GHz 频率下实现了持续每核心 6.0 IPC（每线程 3.0 IPC），分支预测命中率高于 99.8%，L2 缓存命中率高于 99.99%——换句话说，只有当软件层不再成为拖累和瓶颈时，这颗芯片才能展现出真正的恐怖威力，而这才是回答“CPU 算力是否陷入停滞”的真正标准答案。

讨论帖中另一个不那么中听的反馈同样值得注意：许多用户自发抱怨消费级桌面 Ryzen 在主板和 CPU 搭配上的故障率，华擎（ASRock）被多次点名，且现场没人能给出圆满的技术解释。当一个平台的硬件可靠性在坊间沦为靠运气的传闻时，用户的升级意愿自然会大打折扣——这无形中削弱了上述硬核数字原本应当带动的换代热潮。最形象的对比来自历史维度：Ryzen 之于 AMD，正如 Nehalem 和 Core 架构之于当年的 Intel，而 2010 年代惨淡的 FX 推土机系列正是缺少这种突破时的灾难写照。

## 微软在 2007 年杀死了 FoxPro。无论如何，FoxPro 复活了
**452 points** · [foxscript.org](https://foxscript.org/)

FoxDev Studio——FoxScript 的运行时环境与集成开发环境（IDE）——能够直接就地打开现有的 Visual FoxPro 项目、表单、类库、菜单、报表和数据表，全程无需任何格式迁移或数据导出。它的核心卖点是将“行为保真度（Behavioral Fidelity）”奉为一项严肃的工程准则，而非单纯的营销宣传：运行时的行为准则不是靠阅读文档凭空猜测，而是通过直接向 Visual FoxPro 本身发起查询并精确比对输出结果来确立的。项目团队公开了测试覆盖率指标：VFP 9 语言参考规范中的 1,722 个语言元素已全部被运行时识别，其中 1,534 个元素通过了与原版软件输出严格比对的自动化测试，仅剩 3 个名称尚未完全实现。编译器与字节码解释器采用 Rust 编写并编译为 WebAssembly，用户代码以 Fiber 纤程方式运行并向宿主让出控制权而非陷入阻塞，且编辑器内部的代码检查（Linting）直接复用了运行时的同一套编译器——这意味着凡是被波浪线标记的代码，在真实执行时也必然报错。

相比于怀旧情怀，该项目在原版基础上的两项重大技术升级更具实质意义。首先，全盘迈入 64 位时代：文件偏移量由有符号 32 位的 2,147,483,647 字节上限扩展至 64 位，数据表无需整体读入内存，原本 2 GB 的表文件和备注字段（Memo）上限被一举拉高到了数百 GB 级别。开发团队发布的警告也非常坦诚而硬核——一旦 `.dbf` 文件大小突破 2 GB，它将永远无法在原版 Visual FoxPro 中重新打开；如果你跨环境协作，这将是一扇不可逆的单向门。其次，32 位生态兼容性通过独立的宿主进程（Host Process）得以解决：64 位动态库在进程内直接加载，而传统的遗留 `.fll` 扩展则在专用的 32 位垫片进程中运行，二者通过 `SET LIBRARY TO fllhost.exe` 这一缝隙进行交互。这是一个极其高明的架构决策——假装 32 位 COM 组件和 FLL 扩展不存在，只会让这款工具对最迫切需要它的人群毫无用处。

讨论帖中指出的实质性隐患集中在安全性上，而官方网站对此并未正面回应。Visual FoxPro 的数据库容器（DBC）本质上没有任何权限控制模型：为了能正常使用，DBC 必须对所有用户开放读写权限，其存储过程（例如触发器）以明文形式直接保存在备注字段中，并且这些存储过程能够调用包括 Win32 API 在内的任意底层 FoxPro 代码。这意味着共享网络驱动器上的 DBC 实际上是一个完全可写、明文存储、且诞生时间早于“软件供应链安全”概念的任意代码执行攻击面。复活 IDE 并没有凭空制造这一漏洞——它只是在 2026 年的现代机器上全盘继承了它。讨论帖的另一半内容则揭示了该项目为何依然能大获成功：如今依然在使用 FoxPro 的企业往往体量庞大、极度保守，且对激进的代码重写毫无兴趣。一位评论者在刷帖时向业内熟人求证并得到了肯定的答复：时至 2026 年，在一个估值百亿美元的特定行业细分市场中，底层核心依然稳固运行在 FoxPro 之上。这项逆向工程完成度极高，但在讨论帖中无人能够解答的是：当这个经典运行时获得了通往未来的 64 位全新通道时，其裸奔的 DBC 安全机制究竟该何去何从。

讨论帖中的质疑声音十分务实，主要集中在建造成本而非设计概念本身。现场照片中展示的大跨度钢结构支撑造价不菲，一位评论者提出了一个极具先验说服力的对照方案：为什么不把光伏板直接铺在运河旁的开阔农田里，而在运河上方只搭建廉价的纯遮阳网？这个疑问的价值在于它完全可被经验量化检验，而试点项目的初衷正是为了验证这一成本效益：测试三种设计，其中专门包含一种低成本可折叠方案，正是为了给出严谨的对照数据。此外，在水库规模上早已存在验证“遮阳优先”逻辑的现实证据：加州多年来一直在水库中倾倒数以百万计的黑色遮阳球，其目的完全一致。最一针见血的质问在于：加州几十年来为何始终不做这种廉价版的防蒸发改造？其症结显然不在于工程技术。而最具启发性的提问则最为质朴：*为什么不直接沿着运河种树？* 答案在于：树木需要持续消耗水分、需要后期维护，且需要数十年才能成材；而太阳能电池板在遮阴的同时能够自行产生经济收益来抵偿成本。这不是一句辩驳，而是一个清醒的技术经济学抉择，也是该试点项目试图精确测算的核心权衡。

## SAML：糟糕设计的分形结构
**331 points** · [Trail of Bits](https://blog.trailofbits.com/2026/09/21/saml-a-fractal-of-bad-design/)

双方的反驳既合情合理又各自留有盲区。在企业级单点登录（SSO）场景中，SAML 至今依然承担着 OIDC 处理得非常糟糕的特定功能——最典型的便是 IdP 发起的登录流（IdP-initiated flow）；且业内被广泛实现的 SAML 子集在平庸中维持着一种脆弱的稳定性，反观 OIDC 则是一个厂商支持参差不齐、规范分散庞杂的碎片化生态圈。对该博文的一项客观批评同样成立：文章详尽剖析了 SAML 的漏洞历史，却未对 OIDC 实施同样严格的安全审计——而 OIDC 同样有着一长串臭名昭著的经典漏洞模式（JWT 算法混淆、接受 `none` 签名算法、漏检 audience 字段、JOSE 基础库实现缺陷等）。一句极具穿透力的话重塑了整场辩论的维度：当你历经千辛万苦终于完成向 OIDC 的技术迁移后，未来三年你将深陷于不同身份提供商之间 SCIM 协议各种诡异不兼容的无尽泥潭中。协议本身从来不是核心死结所在；协议只是让这个系统性顽疾显得稍微清晰可见的地方。

## WordPress：导致条件性 RCE 的未经身份验证路径遍历漏洞

更令人触目惊心的是官方受影响版本清单，这绝非某个孤立分支上的偶发代码回退。从 4.7 到 7.1.1 的每一个中间小版本全线沦陷，且安全补丁一路向后回溯移植（Backport）修复到了极其古老的 4.7 分支。对于 WordPress 而言，这是一种极不寻常的超长周期维护动作；一位跟帖读者做出了极具价值的算术推导：官方的长期回溯修复固然体现了一种负责任的态度，但也无情地表明该 Bug 的底层逻辑缺陷已经潜伏了超过整整十年，且全球约有三分之一的 WordPress 存量站点根本没有运行在当前最新的大版本分支上。对于插件生态与云托管服务商而言，残酷的现实在于修补窗口期即是彻底裸奔的风险期：这不是一个可以通过修改几项 Nginx 配置就能巧妙规避的漏洞，且那两项触发前置条件全属于根本无人进行安全审计的主题生态特性，其维护者也早已被排除在核心安全通告的圈子之外。

讨论帖中最具普适价值的两条见解完全超越了 WordPress 这一特定系统本身。`libpathrs` 的核心贡献者剖析了这类漏洞的本质通病：此类路径遍历 Bug 之所以反复发作，是因为几乎所有主流编程语言的标准库都将“全局绝对路径”作为最核心的文件操作抽象，而非提供基于作用域的沙盒路径或文件描述符（File Descriptors）；这导致对 `..` 相对路径和软链接（Symlink）的正确安全校验变成了每一个上层应用都必须重复造轮子的苦差事，且绝大多数应用往往会实现得漏洞百出。第二项见解则是一个生动的“弃坑脱逃”样本——一位站长分享称，自己此前借助 Codex 将整个 WordPress 站点彻底重构成了基于 Hugo 的静态模板并部署在静态托管上，自此再也无需承担任何安全运维的心惊肉跳。这既是对 WordPress 固有安全风险最彻底的防御答卷，也是一句残酷的行业大实话：当市面上有了成熟轻便的现代替代品时，老牌 CMS 曾经引以为傲的市场垄断地位，如今在某种意义上已经变成了一项需要被全行业在风险定价中扣除的纯负债。

## Unreal Agent
